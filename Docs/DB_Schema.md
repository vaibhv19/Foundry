# DB_Schema.md — Foundry Database Architecture

This document defines the relational data model for **Foundry**. The schema is optimized to support multi-agent state persistence, granular version control for blueprint sections, and the high-precision retrieval required by the **Decision Memory Engine**.

## 2. Table Dictionary

1.  **`users`**: Core identity and authentication table.
2.  **`ideas`**: Immutable storage of the original one-paragraph startup concepts submitted by users.
3.  **`blueprints`**: The primary container for a startup plan; tracks overall blueprint lifecycle state and ownership.
4.  **`sections`**: Logical divisions of a blueprint (e.g., Market Positioning, Technical Architecture).
5.  **`versions`**: Incremental snapshots of section content; every AI regeneration or manual edit creates a new record here.
6.  **`decision_log`**: The **Decision Log** source of truth; stores normalized, atomic choices made by agents.
7.  **`jobs`**: Scheduling layer for Celery/LangGraph work; tracks requested runs and their lifecycle state.

### 3.3 `blueprints`

### 3.4 `sections`
| Column | Type | Constraints |
| :--- | :--- | :--- |
| `id` | `UUID` | PK |

### 3.5 `versions`
| Column | Type | Constraints |
| :--- | :--- | :--- |
| `id` | `UUID` | PK |

| `version_number` | `INT` | Auto-increment per section |

### 3.6 `decision_log` (The Decision Log Core)
This table is queried whenever a section is regenerated to prevent logical drift.
| Column | Type | Constraints |
| :--- | :--- | :--- |
| `decision_id` | `UUID` | PK |
| `blueprint_id` | `UUID` | FK (blueprints.id) |
| `created_by_version_id`| `UUID` | FK (versions.id) - Which gen attempt made this? |
| `node_origin` | `ENUM` | `INVESTOR`, `PM`, `TECH_LEAD`, `CONSISTENCY_CHECK` |
| `decision_key` | `VARCHAR(100)`| Slug: e.g., `primary_database` |
| `choice_value` | `TEXT` | e.g., `PostgreSQL` |
| `rationale` | `TEXT` | Extracted reasoning for the Decision Memory UI |
| `supersedes_id` | `UUID` | FK (decision_log.decision_id) - Self-reference for overrides |
| `is_active` | `BOOLEAN` | If FALSE, this decision was overridden by user |

### 3.7 `jobs`
| Column | Type | Constraints |
| :--- | :--- | :--- |
| `id` | `UUID` | PK (Matches Celery `task_id`) |
| `blueprint_id` | `UUID` | FK (blueprints.id) |
| `target_section_id` | `UUID` | FK (sections.id), Nullable if initial gen |
| `task_type` | `ENUM` | `INITIAL_DEBATE`, `SECTION_REGEN` |
| `status` | `ENUM` | `PENDING`, `RUNNING`, `COMPLETED`, `FAILED` |
| `current_node` | `VARCHAR(50)` | e.g., `Investor` (Updates Channels UI) |
| `error_log` | `TEXT` | Traceback if status is FAILURE |

`jobs` is the scheduling layer. It records work requests and their lifecycle state. `agent_runs` is the execution layer. It records the actual LangGraph run and the node-level activity for one concrete execution attempt.

### 3.8.6 Suggested Indexes
- `decision_log(blueprint_id, is_active)`
- `versions(section_id, version_number)`
- `agent_runs(blueprint_id, status)`
- `generation_events(blueprint_id, created_at)`
- `exports(blueprint_id, created_at)`

### 3.8.7 Relationship Notes
- `blueprints` has one-to-many relationships to `agent_runs`, `generation_events`, `exports`, and `attachments`.
- `agent_runs` has one-to-many relationships to `agent_messages`.
- `versions` remain the authoritative content snapshots for section regeneration and rollback.

## 4. Key Retrieval Logic: The "Consistency Join"

When a user requests a regeneration for a **Tech Stack** section (Flow 3), the backend executes the following logic:

1.  **Identity:** Locate the `blueprint_id` for the target section.
2.  **Retrieve Commitments:** 
    ```sql
    SELECT decision_key, choice_value, rationale 
    FROM decision_log 
    WHERE blueprint_id = :id AND is_active = TRUE;
    ```
3.  **Inject:** These key-value pairs are injected into the LangGraph state before the agent node executes.
4.  **Update:** If the agent node proposes a new decision (User Override), the system inserts a new `decision_log` row and updates the `supersedes_id` of the previous active row with the same `decision_key`.
